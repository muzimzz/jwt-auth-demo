## 1. JWT란

`Header.Payload.Signature` 세 부분을 base64url로 인코딩해서 이어붙인 토큰.

- **Header**: 알고리즘 정보 (HS256, RS256 등)
- **Payload**: 클레임(claims) — `sub`(주체), `exp`(만료시간), `iat`(발급시간), 커스텀 클레임(권한, 유저ID 등)
- **Signature**: Header+Payload를 서버 비밀키(혹은 개인키)로 서명한 값

> **핵심**: 서버가 별도 저장소 조회 없이 **서명 검증만으로** 토큰의 진위와 내용을 신뢰할 수 있음.
> Payload는 암호화가 아니라 인코딩 — 누구나 디코딩해서 내용을 볼 수 있음. 서명은 **신뢰성**을 보장하는 것이지 **기밀성**을 보장하는 게 아니므로 민감정보는 절대 넣지 않는다.

## 2. 세션 대신 JWT를 쓰는 이유

세션 방식: 서버가 `session_id → 유저정보` 매핑을 서버 메모리/Redis에 보관. 매 요청마다 저장소 조회 필요.

| 구분 | 세션 | JWT |
|---|---|---|
| 상태 저장 위치 | 서버 (stateful) | 클라이언트 (stateless) |
| 검증 방법 | 저장소 조회 | 서명 검증 (계산만) |
| 서버 확장성 | 세션 클러스터링/스티키세션/Redis 공유 필요 | 서버 아무거나 붙어도 됨 |
| 즉시 무효화 | 서버에서 세션 삭제하면 끝 | 어려움 (블랙리스트 필요) |

**JWT를 쓰는 근본 이유**: stateless라서 서버 수평 확장이 쉽고, MSA 환경에서 여러 서비스가 세션 저장소를 공유하지 않고도 인증 정보를 검증할 수 있음. 대가로 "즉시 무효화가 어렵다"는 단점을 얻음.

## 3. 액세스 토큰만 쓰면 왜 문제인가

**문제는 탈취 대응과 만료시간의 트레이드오프.**

- 만료시간을 **길게** → 탈취 시 공격자가 오래 사용 가능. stateless라 강제 무효화 수단이 마땅치 않음.
- 만료시간을 **짧게** → 탈취 피해는 줄지만, 사용자가 몇 분마다 재로그인해야 해서 UX 저하.

→ 절충안: **액세스 토큰은 짧게, 대신 리프레시 토큰으로 자동 재발급**.

---

## 4. 리프레시 토큰을 쓰는 이유

| | 액세스 토큰 | 리프레시 토큰 |
|---|---|---|
| 수명 | 짧음 (15분~1시간) | 김 (며칠~수주) |
| 용도 | 매 API 요청 검증 | 액세스 토큰 재발급 전용 |
| 상태 관리 | Stateless (기본) | Stateful (DB/Redis 저장) |

리프레시 토큰은 "긴 세션 유지"와 "탈취 피해 최소화"라는 상충하는 요구를 **분리**해서 해결하는 장치. 액세스 토큰은 stateless로 두고 리프레시 토큰만 stateful하게 관리하면, stateless의 확장성과 강제 로그아웃 가능성을 동시에 확보할 수 있음.

---

## 5. 액세스 토큰 탈취 시 대응

- **짧은 만료시간**: 탈취돼도 곧 자동 무효화
- **블랙리스트 체크**: 강제 무효화가 필요할 때 Redis에 무효화 목록(jti)을 두고 매 요청마다 확인
- **HTTPS 필수**: 전송 구간 탈취 자체를 차단
- **payload 최소화**: 민감정보 미포함으로 탈취 시 노출 정보 최소화
- **저장 위치**: localStorage는 XSS에 취약 → 가능하면 httpOnly Secure 쿠키 권장 (단, 이 경우 CSRF 대응 별도 필요)

---

## 6. 리프레시 토큰 탈취 시 대응

리프레시 토큰은 수명이 길어 탈취 시 피해가 훨씬 큼(공격자가 계속 액세스 토큰 재발급 가능). 방어를 더 두껍게:

- **httpOnly + Secure + SameSite 쿠키**에 저장 (JS 접근 불가, XSS 방어) — localStorage 사용 금지
- **서버 측(DB/Redis) 상태 관리**: 탈취 의심 시 즉시 삭제 → 재발급 불가
- **재발급 엔드포인트 별도 보호**: rate limit, IP/기기 정보 검증
- **RTR (Refresh Token Rotation)** 적용 → 7번 참고

## 7. RTR (Refresh Token Rotation)

**핵심 아이디어**: 리프레시 토큰을 재사용 불가능한 1회용(one-time-use)으로 만든다.

### 동작 방식

1. 클라이언트가 리프레시 토큰으로 재발급 요청
2. 서버는 새 액세스 토큰 + **새 리프레시 토큰**을 발급하고, 기존 리프레시 토큰은 DB에서 즉시 폐기
3. 클라이언트는 새 리프레시 토큰으로 교체 저장

### 탈취 탐지 원리

```
공격자가 리프레시 토큰 A를 탈취했다고 가정

Case 1) 정상 유저가 먼저 A로 재발급
  → A 폐기, B 발급
  → 공격자가 나중에 A로 시도 → 이미 폐기된 토큰 → 실패

Case 2) 공격자가 먼저 A로 재발급
  → A 폐기, B 발급 (B는 공격자가 보유)
  → 정상 유저가 여전히 옛 A로 요청
  → 이미 폐기된 토큰 재사용 시도 감지!
  → 이런 상황은 정상적으로는 절대 발생 불가
  → 해당 토큰 체인(family) 전체 강제 무효화 + 재로그인 요구
```

**정리**: RTR은 탈취된 토큰의 유효기간을 사실상 "다음 정상 요청 전까지"로 극단적으로 줄이고, 탈취를 사후에 탐지할 수 있는 로직까지 함께 제공하는 기법.

### 전체 흐름 요약

```
로그인
 → 액세스 토큰(짧음, stateless, 매 요청 검증)
   + 리프레시 토큰(김, 서버 상태 저장, httpOnly 쿠키)

액세스 토큰 만료
 → 리프레시 토큰으로 재발급 요청
 → RTR: 기존 리프레시 토큰 폐기 + 새 액세스/리프레시 토큰 쌍 발급
 → 이미 폐기된 리프레시 토큰으로 요청 들어오면 = 탈취 의심 → 전체 세션 무효화
```

## 8. 블랙리스트(토큰 무효화) 자세히

### 왜 필요한가

JWT는 stateless라 발급되면 서명이 유효하고 만료 전이면 서버가 막을 방법이 원래 없음.  
그런데 로그아웃, 비밀번호 변경, 관리자 강제 차단, 탈취 의심 상황에서 "아직 안 만료됐지만 더는 유효하지 않다"고 선언할 수단이 필요 → 블랙리스트.

### 구조

```
key   : blacklist:{jti}          (또는 blacklist:{token해시})
value : "revoked" (또는 사유)
TTL   : 해당 토큰의 남은 만료시간까지
```

**TTL을 토큰의 남은 만료시간으로 맞추는 것이 핵심.** 토큰은 어차피 `exp` 시점에 자동 만료되므로, 그 이후까지 블랙리스트에 남길 필요가 없음 → 블랙리스트 크기가 무한히 커지지 않음.

### 검증 흐름

```
요청 도착
 → JWT 서명/만료 검증 (기존과 동일)
 → 통과 시 Redis에 blacklist:{jti} 존재 여부 조회
 → 존재하면 401, 없으면 정상 처리
```

Redis 조회 1회 추가 — 완전 stateless는 아니지만 DB 풀스캔/세션 저장소 조회보다 훨씬 가벼움. JWT의 성능 이점을 크게 해치지 않으면서 즉시 무효화도 가능.

### jti 클레임을 쓰는 이유

- payload에 `jti`(JWT ID, 발급 시 UUID 부여)를 넣고 이를 키로 사용
- 토큰 전체 문자열보다 짧아 저장/조회 효율적
- 같은 유저의 여러 기기 로그인을 개별 식별 가능 (기기별 로그아웃 등에 활용)

### 블랙리스트 vs 화이트리스트

| | 블랙리스트 | 화이트리스트 |
|---|---|---|
| 기본 동작 | 다 허용, 무효화된 것만 차단 | 목록에 있어야만 허용 |
| 저장 부담 | 적음 (무효화된 것만) | 큼 (발급된 전체) |
| 성격 | Stateless에 가까움 | 사실상 세션 방식으로 회귀 |

실무에서는 **액세스 토큰엔 가벼운 블랙리스트**, **리프레시 토큰엔 DB에 화이트리스트(전체 관리)**를 쓰는 하이브리드 구성이 흔함. "이 유저의 활성 세션 목록 보여주기" 같은 기능이 필요하면 화이트리스트 성격의 관리가 필요.

### 로그아웃 처리 흐름

1. 액세스 토큰의 `jti`를 블랙리스트에 등록 (TTL = 남은 만료시간)
2. 리프레시 토큰은 DB/Redis에서 레코드 자체를 삭제

## 9. 토큰 저장 형태 정리

| 항목 | 액세스 토큰 | 리프레시 토큰 |
|---|---|---|
| **본질** | JWT (서명된 토큰 자체) | JWT일 수도, 랜덤 opaque 문자열일 수도 있음 |
| **서버 저장 여부** | 기본은 저장 안 함 (stateless) | **저장함** — DB 또는 Redis에 레코드 유지 |
| **무효화 시 저장 형태** | Redis 블랙리스트: `blacklist:{jti} = revoked`, TTL = 남은 만료시간 | DB/Redis에 `token(또는 해시) ↔ userId ↔ 만료시간 ↔ 상태` 형태로 저장, 폐기 시 레코드 삭제 또는 상태값 변경 |
| **클라이언트 저장 위치** | httpOnly Secure 쿠키 권장 (localStorage는 XSS 취약) | httpOnly Secure SameSite 쿠키 (localStorage 절대 금지) |
| **DB 저장 시 컬럼 예시** | (보통 DB에 안 넣음) | `id, user_id, token_hash, issued_at, expires_at, revoked_at, replaced_by(RTR 체인 추적용)` |
| **평문 저장 여부** | 해당 없음 | **해시로 저장 권장** (DB 유출 시 그대로 악용되지 않도록, 비밀번호처럼 취급) |

> 리프레시 토큰을 DB에 저장할 때도 **원문이 아니라 해시값**을 저장하는 것이 원칙. 검증 시 클라이언트가 보낸 토큰을 같은 방식으로 해시해서 DB 값과 비교. DB 덤프가 유출되더라도 토큰 원문이 그대로 노출되지 않도록 하기 위함.

## 10. HTTPS 외의 탈취 경로

HTTPS는 "전송 중" 탈취(네트워크 스니핑, MITM)만 막아줌. 실무에서는 다른 경로가 더 흔함.

| 경로 | 설명 | 방어책 |
|---|---|---|
| **XSS** | 악성 스크립트가 `localStorage.getItem('token')`으로 직접 탈취 | httpOnly 쿠키, CSP, 입력 이스케이프 |
| **CSRF** | 쿠키 자동 첨부 특성을 악용해 몰래 요청 대신 전송 (탈취보다는 도용) | SameSite 쿠키, CSRF 토큰 병행 |
| **로컬 기기/악성 확장 프로그램** | 공용 PC, 분실 기기, 악성 브라우저 확장이 저장소 직접 접근 / 콘솔 붙여넣기 소셜엔지니어링 | 사용자 교육, 기기 신뢰도 검증 |
| **로그/모니터링 유출** | access log에 Authorization 헤더, 에러 모니터링 툴(Sentry 등)에 요청 캡처되며 노출 | 토큰 로그 미기록, 헤더 마스킹 |
| **URL 쿼리스트링 노출** | 브라우저 히스토리, 프록시 로그, Referer 헤더로 유출 | 쿼리스트링에 토큰 절대 미포함 |
| **모바일 앱 환경** | 루팅/탈옥 기기의 저장소 직접 접근, 리버스 엔지니어링, 인증서 피닝 미적용 시 MITM 프록시(Charles, Burp Suite) 우회 | 인증서 피닝, 루팅 탐지 |
| **서버 사이드 유출** | DB 덤프 유출 시 리프레시 토큰 평문 노출 / 시크릿 키 유출로 토큰 위조(sign) | 토큰 해시 저장, Vault/KMS로 키 관리, 하드코딩 금지 |

> "탈취당한 뒤 대응"(블랙리스트, RTR)과 "애초에 탈취 경로를 줄이는 것"(저장 위치, 로깅 정책, 인증서 피닝)은 서로 다른 층위의 방어이며, 실무에서는 둘 다 함께 적용해야 함.
